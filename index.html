          Secure sign-in, explained

          Two terms get mixed up all the time. OAuth 2.0 is the process that lets one app act for you without ever seeing your password. A JWT is a signed token that proves who you are and what you're allowed to do. I use both in production integrations.

          OAuth 2.0

          The permission process

          Answers
          May this app access my data, and which parts?
          You see it as
          “Connect with HubSpot” or “Sign in with Microsoft”
          The app receives
          A short-lived access token and a longer-lived refresh token

          JWT

          A signed token

          Answers
          Is this token genuine, and what does it say about the caller?
          You see it as
          Three dotted parts: header.payload.signature
          The API checks
          The signature, the expiry time, and who it was issued for

          How they fit together: OAuth 2.0 is how an app gets a token. The token is often a JWT. The API then checks the JWT's signature and expiry on every request.

          OAuth 2.0: connecting an account, step by step

          The authorization code flow, the standard way to let an app connect to HubSpot, Microsoft or Shopify. Step through it and watch what is sent and why it is safe.

          Youyour browser
          My appmy server
          Auth serverthe login page
          APIthe data

          
          
          
          
          
            
            
            
          
          
        
          
      
          
      
          See it in code: my integration-starter-kit implements this flow, plus encrypted token storage and a lock so only one refresh runs at a time. Not every provider supports PKCE yet. When one doesn't, the state check and the client secret kept on my server protect the flow.
          

      
          JWT: why a token can be trusted
          
      
          This token is signed with a secret key that only the server knows. Try to cheat with it and watch the server reject you. The check is really computed in your browser.
          
      
          
        
          
          
          
          
            Header: how it's signed
            Payload: who and what
            Signature: the proof
          
          
          
          
            
            
            
            
          
          
        
          
        
          
          
          Header (decoded)
          
          
          Payload (decoded)
          
        
          
        
          
          
          
          
            
        
            
        
            Good to know: anyone can read a JWT's payload. It is encoded, not encrypted, so never put passwords or secrets in it. The signature is what stops changes. Real systems often use RS256, where a private key signs and a public key verifies, so APIs can check tokens without holding the signing secret.
